# ADR-002: 为什么用文件而非数据库存储

> 状态：已接受
> 日期：2026-07-29

## 背景

Paper-Glean 需要持久化论文数据、兴趣画像和反馈记录。传统应用会选择数据库，但本项目有特殊考量。

## 考虑的方案

| 方案 | 优点 | 缺点 |
|------|------|------|
| **A: 文件存储（Markdown + JSON）** | 人类可读、Git 版本化、可手工编辑、零依赖 | 查询效率低、无事务、无索引 |
| **B: SQLite** | 结构化查询、事务、轻量 | 非人类可读、需 schema 迁移、与 Git 协作困难 |
| **C: PostgreSQL** | 功能完整、性能高 | 需安装服务、运维负担、违背本地优先 |

## 决策

选择 **方案 A：Markdown + JSON 文件存储**

## 理由

1. **人类可读**：`interests.md` 和 `arXiv-schedule.md` 可直接用 Obsidian/VS Code 打开编辑
2. **Git 版本化**：每次 fetch 和 feedback 都是可 diff 的变更
3. **零依赖**：不需要安装/启动数据库服务
4. **本地优先**：数据完全在用户控制下，可随时导出/迁移
5. **CLI fallback**：即使 Web 应用不可用，文件仍然可读可编辑

## 数据文件设计

| 文件 | 格式 | 用途 | 读写模式 |
|------|------|------|----------|
| `data/YYYYMMDD.json` | JSON | 每日论文原始数据 | 写（fetch 时） |
| `interests.md` | Markdown | 兴趣画像 | 读写 |
| `feedback.jsonl` | JSON Lines | 反馈日志 | 追加 |
| `arXiv-schedule.md` | Markdown | 人读 digest | 读写 |

## 性能考量

- **查询效率**：当前数据量（每日 < 500 篇）下，内存中过滤足够快
- **索引**：如需加速，允许增加可随时删除重建的只读索引缓存
- **原子写入**：使用 "写临时文件 + os.replace()" 模式保证安全

## 后果

### 正面
- 极简架构
- 完全可控
- 与 Obsidian 工作流无缝集成

### 负面
- 无法做复杂查询（如跨日期的全文检索）
- 并发写入需文件锁保护
- 数据量增大后可能需要索引缓存
