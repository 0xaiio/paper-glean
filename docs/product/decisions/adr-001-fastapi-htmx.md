# ADR-001: 为什么选择 FastAPI + HTMX 而非 React/Vue

> 状态：已接受
> 日期：2026-07-29

## 背景

M1 需要为 Paper-Glean 构建 Web 界面。前端技术栈的选择直接影响开发效率、维护成本和用户体验。

## 考虑的方案

| 方案 | 组成 | 优点 | 缺点 |
|------|------|------|------|
| **A: FastAPI + HTMX/Alpine.js** | 服务器渲染 + 轻量 JS | 零构建链、与 Python 同栈、CLI 共享函数、数据不出机 | 界面上限受限于服务器渲染 |
| **B: SvelteKit/React + FastAPI** | 前后端分离 | 界面上限高、虚拟滚动/动画更顺 | 构建链重、维护成本↑、状态同步复杂 |
| **C: Flask + Jinja2** | 传统服务器渲染 | 简单、成熟 | 异步支持弱、生态落后于 FastAPI |

## 决策

选择 **方案 A：FastAPI + HTMX + Alpine.js**

## 理由

1. **与现有资产同栈**：项目已有 Python 核心库，无需引入 Node.js 构建链
2. **零迁移承诺**：Web 与 CLI 调同一套 `glean/core.py` 函数，逻辑不重写
3. **本地优先契合**：单进程运行，数据不出机，无需处理前后端状态同步
4. **维护成本低**：HTMX 的 "HTML over the wire" 模式使前端代码量极小
5. **足够好的体验**：M1 场景（浏览、筛选、打分）不需要复杂的客户端交互

## 后果

### 正面
- 开发速度快（M1 一天内完成）
- 代码量少（前端 < 200 行 JS）
- 无需构建步骤

### 负面
- 虚拟滚动等高级交互需要额外处理
- 动画效果有限
- 长期看可能需要迁移到方案 B（M3+）
