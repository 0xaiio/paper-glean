# 设计原则

> 贯穿所有功能取舍的四条原则

## 1. 本地优先（Local-first）

**原则**：数据全部落在本仓库内，可 Git 版本化、可离线、可随时退出；不引入云端账号体系。

**实践**：
- 所有数据文件（`data/*.json`, `interests.md`, `feedback.jsonl`）都在仓库内
- Web 应用只是视图层，不引入数据库
- 可选的只读索引缓存（如 SQLite）必须可随时删除重建

**反模式**：
- ❌ 用户注册/登录系统
- ❌ 云端同步服务
- ❌ 第三方数据存储

## 2. Markdown/JSON 为唯一事实源

**原则**：Web 应用只是「视图层」，`interests.md`、`data/*.json`、`feedback.jsonl`、`arXiv-schedule.md` 仍是权威数据；文件可随时手工编辑，Web 端读写的就是这些文件。

**实践**：
- Web 端的任何修改立即写回文件
- 文件手工编辑后 Web 端自动重载
- 所有数据格式对人类可读

**反模式**：
- ❌ Web 应用有自己的数据库
- ❌ 数据格式只有程序能读
- ❌ 文件与 Web 状态不同步

## 3. CLI 永远是 fallback

**原则**：Web 挂了脚本照跑；任何 Web 功能都不得使 CLI/Obsidian 工作流失效。

**实践**：
- `glean/core.py` 的纯函数同时被 CLI 和 Web 调用
- CLI 保持零外部依赖（标准库即可运行）
- `arXiv-schedule.md` 继续生成，Obsidian 阅读不受影响

**反模式**：
- ❌ Web 独占某些功能
- ❌ CLI 依赖 Web 服务启动
- ❌ 数据格式变更破坏既有工作流

## 4. 可解释推荐

**原则**：每条推荐必须能回答「为什么推荐给我」——命中了哪个画像条目、权重得分多少、agent 给出什么理由。拒绝黑盒。

**实践**：
- 每篇论文显示命中的兴趣条目和权重
- 推荐表中给出 agent 的中文推荐理由
- `feedback.jsonl` 记录完整的决策审计轨迹

**反模式**：
- ❌ "你可能喜欢这篇论文"（无理由）
- ❌ 隐藏推荐算法的内部逻辑
- ❌ 无法追溯某次推荐的依据
